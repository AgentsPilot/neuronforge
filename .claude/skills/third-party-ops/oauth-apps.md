## 1. What must differ between environments

The **current** setup (which Microsoft registration each environment's MX names belong to, and whether one registration serves several environments) is recorded in the private inventory by role, checked at use time, and reported by role.

## 4. Probes

Each fails when the setting is wrong. None sends mail, creates, moves or deletes a calendar event, drafts a reply, enables calendar sync or the inbox channel, or connects a real account (except the optional, user-approved P-OA-5); none needs DO to hold a key, prints a value or runs in a loop. Each runs on the deployment named per `vercel-ops` §4, after it is Ready. A 401 from deployment protection, or any answer that is not the route's own, is "not probed (protected host)". OneDrive and AT to SF have no probe: "not probed (no live path)" (OA-1).

**Refresh outcome lines** (P-OA-4, P-OA-4b, T-OA-7): module `UserPluginConnections`, `pluginKey` `outlook`, on the deployment under test. S = "Token Refresh Success - New token saved"; T and R = "Token refresh failed" with `reason` `transient` and `grant_revoked`. "Token Refresh: Attempting to refresh token" is context, never the denominator (OA-4).

**Rotation overlap.** While the old secret is still valid at the vendor, a pass of P-OA-4, P-OA-4b or P-OA-5 may have used it (for example if the new value never reached the target), so it is "pass, not conclusive (overlap)". It proves the target for the §7 delete only when it comes from a deployment that carries the new value: one created after the name's last-updated time on that target (`vercel-ops` §3 and §4), with the user's report that this time is after the new secret was added. After the delete, P-OA-4 is read again on each target (P-OA-4b or P-OA-5 where it does not read); only a pass after the delete is conclusive.

## 5. Gotchas

1. **Only Outlook is loaded** (OA-1). A OneDrive, Airtable, Discord, Dropbox, HubSpot, LinkedIn, Notion or Salesforce failure is never read as a credential fault (`messaging.md` MS-1).
2. **One client, two plugins** (OA-2): a secret change touches Outlook and OneDrive, and every environment that shares the registration.
3. **Refresh uses the secret** (OA-3): a secret change reaches every stored Outlook connection at its next refresh, from any of the four callers, not only new connects. This differs from Meta (`messaging.md` MS-5).
4. **A bad or expired secret reads as transient** (OA-5): no connection is marked and no readiness warning appears. The refresh outcome count is the only signal.
5. **Match refresh lines exactly** (OA-4): "Token refresh failed" is logged by several modules, some with `pluginKey`. Count the `UserPluginConnections` line, by `pluginKey` and `reason`.
6. **The client secret expires on a date set at creation** (vendor fact, confirm at use time): expiry is planned drift (T-OA-5), never a surprise.
7. **Unset is not refused by our code** (`messaging.md` MS-2): it surfaces as a vendor error page, or at the token exchange.
8. **The callback answers one origin** (`google.md` §5): a connect started from a per-deployment host completes at the vendor, but the page never hears of it.
9. **`/common/` serves two account kinds** (OA-2; vendor fact): a work tenant may also require admin consent or a verified publisher. A pass with a personal account proves nothing for a work account, and the reverse.
10. **The connect surfaces turn features on** (OA-7): a probe never enables calendar sync or the inbox channel.

## 7. Tiers and order against the deploy

**Tiers** (`env-change-protocol`; nothing restated). Production tier (SA reviews the plan, the user executes): on a registration production uses, adding or deleting a client secret, any redirect URI added or removed, any change to supported account types, API permissions, consent or publisher verification; creating a new registration for production (it changes the client ID); removing any of these names from production. A change to a registration used **only** by non-production environments, as recorded, is reversible: the user applies it after the approval in chat. Where one registration serves several environments, every change to it is production tier.

| Change | When |
|---|---|
| Client secret rotation (planned, before expiry) | Add the new secret; the old one stays valid (vendor fact, confirm at use time) → set the new value on **every** target that uses the registration → each deploy Ready → P-OA-2, then the first of P-OA-4, P-OA-4b or P-OA-5 that reads, on each target → delete the old secret only when **every** target is proved (§4 "Rotation overlap") → P-OA-4 again on each target → record the new bucket (T-OA-5). Until every target is proved, the old secret stays on the registration, so a deployment built before the change (an instant rollback) still works; if a target is never proved, the old secret ends on its own expiry date, and T-OA-7 and T-OA-8 watch the window after that date. Deleting the old secret while a target still holds it fails every stored connection there at its next refresh, and it reads as `transient` (OA-5) |
| Client secret exposed | The same order up to Ready on every target, then delete the old secret without waiting for a probe. The plan names the targets not proved as at risk, and T-OA-7 is read in the next window |
| Client secret already expired | Add a new secret → set it on every target → deploy Ready → the first of P-OA-4, P-OA-4b or P-OA-5 that reads, on each target → delete the expired secret → record the new bucket (T-OA-5). Whether existing grants recover at the next refresh without a reconnect, because the client ID is unchanged, is a vendor fact, confirm at use time |
| A new registration (client ID change) | Every existing Outlook connection must reconnect: an owner-facing change, planned and announced as such |
| A new or changed callback path, or a new environment | Its redirect registered for every stable address before merge, or before that environment serves the connect |
| A scope the Outlook definition starts to request | Configured as a permission on the registration (and consented where the vendor requires) before merge. Whether existing connections need to re-consent is a vendor fact, confirm at use time |
| Supported account types narrowed | Only with a plan for the connections of the excluded kind, which fail at their next refresh (vendor fact, confirm at use time) |
| App address moves (`domains.md` §7) | In step 5, add the new redirect URI; remove the old one in step 8 |
| A plugin added to the active profile | This file gains its probe rows and its redirect is registered before merge (T-OA-9) |
| Removing AT to SF or OneDrive names | After FU-D6h-a decides |

**Last-updated time:** where `vercel-ops` §3 shows the name's last-updated time on each target, it is after the new secret was added. Alone it is never a pass; with a probe pass it proves the target for the delete (§4 "Rotation overlap"). Which outcome class a refused or expired secret produces is a vendor fact, confirm at use time; confirm it once on a non-production registration before the first production rotation, and record it in the private inventory.
