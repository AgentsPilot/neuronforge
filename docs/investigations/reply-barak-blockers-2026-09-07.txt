1. THE TWO MIGRATIONS — one of them, not both

business_subdomain is genuinely unapplied. Confirmed:

    business_profiles select=id,subdomain
    42703 column business_profiles.subdomain does not exist

invoice_online_payment is already applied:

    payment_invoices select=id,allow_online_payment  -> OK, rows=1

The column is there and the flow is wired end to end — PaymentRepository, the invoices route's
Zod schema, InvoiceDeliveryService at send time, and the client pay page all read it. Nothing to
do on that one.

On the first one I'd refine the impact rather than the fact. One place does read the column —
resolveBusinessSubdomain, businessSubdomain.ts:41-45:

    .from('business_profiles').select('subdomain, user_code')

and that select does fail, 42703, every call. But it fails softly. The error is destructured away
(`const { data: profile } = await ...`, no error binding), so nothing throws, profile is null, and
execution falls through to the second query against website_pages.subdomain — which exists and
works. That is where every real address actually comes from, via WebsitePageRepository
.findBySubdomain / .findBySubdomainAny and the check_subdomain_available / generate_subdomain RPCs.

So resolution is not broken. What IS dead is the last fallback on line 65:

    return profile?.user_code || null;

profile is always null, so a business with no subdomain on any page can never reach its user_code
and WebsitePublishService:130 refuses the publish with "This page has no web address yet." That is
a genuine publish-blocking path — it just needs a business in that state to bite, and right now
there isn't one:

    users with website_pages: 1
    of those, with no subdomain on any page: 0

So: worth applying, and it closes a real trap that the first business to publish a page without a
subdomain would fall into. Not a live outage today. I'd not rank it first, but I would not leave it
either — it is one migration away from being someone's silent bug.


2. THE THREE client_email DETECTORS — this shipped on 26 Aug

All three already group by contact_id. It's commit 3390050, 2026-08-26, and I confirmed it's an
ancestor of origin/main.

    CrmEngagementDecayDetector        .select('contact_id, start_time')     no client_email anywhere
    PricingIntroOfferStuckDetector    .select('id, contact_id, ...')        comment only
    RetRepeatBookingLowDetector       .select('contact_id, id, ...')        comment only

In the two that still contain the string, it survives only inside a comment recording its removal
— RetRepeatBookingLowDetector line 90 reads "Grouped by contact, not by email text. `client_email`
was dropped". CrmEngagementDecayDetector doesn't contain it at all. So your approach was right; it
is the approach that's already in the tree.

Worth knowing if you grep for this again: client_email IS still a live column on payment_invoices.
Different table, unaffected.

BUT — and this is the part worth your time — your instinct that PricingIntroOfferStuckDetector had
a client_email problem was right, and there's a real bug there the migration missed. Line 147
assigns a contact UUID to a variable still named `email`:

    const email = booking.contact_id;

That flows into stuckEmails, which is then used at line 235 as an email filter:

    .in('email', [...stuckEmails].slice(0, 50))

It matches contact UUIDs against the email column. I probed it with a real booking's contact_id:

    AS-WRITTEN  .in(email,[uuid]) -> err= none  rows= 0
    CORRECTED   .in(id,[uuid])    -> err= none  rows= 1

No error — Postgres compares the UUID as text and matches nothing, so stuckContacts is always
empty. The insight still fires with a correct conversion rate and severity, but names nobody,
which is the only actionable part of it. The stale variable name is what hides it in review.

If you still have that branch open, this is the one-line change actually worth pushing.


3. THE FOUR SCHEMA-BROKEN DETECTORS — three confirmed, and two are worse than you wrote

I executed every query in each file rather than just the one quoted, which changed two of the
answers.

WebMobileIssuesDetector — confirmed, and it's all four queries, not just `websites`:

    websites             42P01 relation "public.websites" does not exist
    website_page_views   42703 column website_page_views.visitor_id does not exist
    scheduling_bookings  42703 column scheduling_bookings.metadata does not exist
    scheduling_bookings  42703 column scheduling_bookings.price does not exist

It fails silently — the first query is guarded by `if (websiteError || !website) return null`, so
it reports "nothing detected" for every user on every run.

WebPageUnderperformDetector — confirmed, four of five fail. Only the crm_contacts query is sound.
website_pages has `slug`, not `path`, and website_page_views has no `page_path`.

PricingDiscountAbuseDetector — confirmed. One precision worth recording: metadata DOES exist on
payment_transactions, so its first query is fine. Only the scheduling_bookings half is wrong. Real
column name, wrong table — that's the shape that keeps getting through review.

OpsPeakUnutilizedDetector — this one I'd class differently. Its detection logic is fine:

    scheduling_bookings select=start_time, status  -> OK, rows=1

Both queries that decide whether to fire work. Only the third query, the one that prices the
finding, fails on `price` (the column is payment_amount). And because it's destructured as
`{ data: avgValue }` with the error discarded, avgValue is null and it falls through to a
hardcoded default at line 176:

    : 75; // Default estimate

So it isn't broken in the sense the others are. It fires correctly and reports a fabricated
missed-revenue number built from $75 a booking. I'd argue that's worse than dead, because the
number looks real and someone will act on it. It also needs a much smaller fix than a rebuild —
swap `price` for `payment_amount`.

On your proposal: both replacement columns are real, I checked.

    scheduling_bookings select=id, booking_source        -> OK
    crm_contacts select=id, source_metadata              -> OK

So rebuilding the two web ones against those is viable. Given both are silently dead today, is
anyone actually reading their output? If not, retiring them is the cheaper answer and I'd support
it — but that's a product call, not mine.


4. GENERATED TYPES — the conclusion is right, the evidence isn't, and the real problem is bigger

@/types/database doesn't exist — confirmed. /types/ has only analytics, pdf-parse, pdfjs-dist,
settings and system-health.

But BusinessProfileRepository.ts doesn't import it. Line 9 is:

    import { supabaseServer } from '@/lib/supabaseServer';

Nothing in the repo imports @/types/database. The only two matches anywhere are comments noting
its absence. And the project typechecks clean:

    npx tsc --noEmit -p tsconfig.json | grep -c "error TS"
    0

Zero errors, no TS2307. I'd want to know where that line reference came from — if it's from an
older checkout, it'd be useful to know which, because it would tell us how stale the rest of the
audit base was.

That said, your actual diagnosis is correct and I'd go further: generating the types would not, on
its own, close the hole. next.config.js has

    typescript: {
      ignoreBuildErrors: true,
    }

so the build discards TypeScript errors regardless. Generated types plus a typecheck gate that
actually fails CI is the fix; generated types alone would give us the feeling of coverage without
the coverage. That's a change I think is clearly worth making, and it's the only item on this list
that prevents the next four of these rather than cleaning up the last four.

6. saved-plans.test.ts

You're right that it reaches the real database. The mechanism isn't the one described, and the
difference matters for the fix.

There are mocks — makeFakeClient() at lines 22-48, injected via new SavedPlanStore(client), and the
docblock says so. The injected client is fine. What escapes it is three un-injected module-level
call sites reached from the applyFrozenWrites test at line 199:

    BusinessProfileRepository.findByUserId   via applyWrites.ts:78 -> lib/email/branding.ts:74
    SystemConfigService.get(...)             via ForEachExecutor.ts:236
    ActionLog.countToday                     via ForEachExecutor.ts:237

All three logged "TypeError: fetch failed" — which is the proof they made a real outbound call.

The reason this is more serious than it looks: tests/plugins/jest-setup.ts stubs the Supabase env
only when it isn't already set —

    process.env.NEXT_PUBLIC_SUPABASE_URL = process.env.NEXT_PUBLIC_SUPABASE_URL || 'https://test.supabase.co';
    process.env.SUPABASE_SERVICE_ROLE_KEY = process.env.SUPABASE_SERVICE_ROLE_KEY || 'test-service-role-key';

In my run it hit the placeholder host and failed. On any machine or CI job with real Supabase env
exported, those three calls resolve against the real database with the service-role key. I did not
run that variant deliberately — the same test drives a send fan-out and I was keeping this audit
read-only.

Separately, and this is a different defect: the test passes 8/8 in 3.4s but Jest won't exit. I
timed one run out at 6m40s before checking with --detectOpenHandles:

    ●  Timeout
        at AuditTrailService.startFlushTimer (lib/services/AuditTrailService.ts:231)
        at AuditTrailService.getInstance (lib/services/AuditTrailService.ts:63)

A module-level getInstance() starts a setInterval flush timer that's never cleared. Mocking
