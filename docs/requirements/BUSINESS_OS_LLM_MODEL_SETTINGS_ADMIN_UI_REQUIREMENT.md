## Overview

[Layer 2](/docs/requirements/BUSINESS_OS_LLM_MODEL_SETTINGS_LAYER2_REQUIREMENT.md) made every catalogued Business OS AI call read its **provider, model, temperature and on/off switch** from one of eight `system_settings_config` rows at run time. It deliberately shipped **without a screen**: "the admin screen comes in a later layer". This is that layer.

Today changing a Business OS model, or switching an AI area off during a cost incident, requires a terminal, a checked-out repository, a `.env.local` holding the **service-role key**, and `npm run bos:llm-settings`. That is workable for one person and impossible for everyone else — including the person who is actually on call. The [operator runbook](/docs/runbooks/BUSINESS_OS_LLM_MODEL_SETTINGS_RUNBOOK.md) is the de-facto specification of what an operator needs, and this screen exists to make its §2, §3, §4 and §6 possible from a browser, for a platform admin, with no service-role key in anyone's hands.

**Two things this screen must not become:**

1. **A weaker door than the script.** `scripts/bos-llm-settings.ts` writes nothing that the resolver would refuse to honour, because it validates the candidate row with **the resolver's own** guardrails (`validateAreaRow`). A screen that re-implements "a reasonable-looking form" would be a second, softer way into the same eight rows. It must call the same function (D-3).
2. **A screen that says "off" when off is not guaranteed.** `isBosLlmAreaEnabled` **fails open**: on a cold start or a settings-read failure a switched-off area silently comes back on (runbook §5, FU-6 / D-61). This is the single most dangerous property of the feature, and the screen is the first place where an operator will read a green "Disabled" chip and walk away. It must never make a claim the system does not keep (D-4).

**What an admin can do here:** see, per area, what every catalogued call resolves to, where each value came from, and **who last changed it**; change the model, provider or temperature at area level or for one call; switch an area (or a switchable call) off and on, with the other admins told when that happens; and — after switching off — see ledger **corroboration**, with its limits stated, of whether calls actually stopped.

| # | Decision | Rationale |

| **D-1** | ✅ **The generic route keeps refusing `bos_llm_area_*`. The screen gets its own dedicated route.** `PUT /api/admin/system-config` continues to return 400 for these keys, permanently — its error message changes from "Use `scripts/bos-llm-settings.ts`" to point at the new screen. The generic route's key defences exist because its key is a **free-text input** over a 50-key batch with no dry-run and no per-key audit (G-6), and D-14 says the unit of validation is one whole row. | **D-2** | ✅ **The resolved value is the primary view; the stored row is secondary and explicitly labelled.** Each call shows its resolved `{ enabled, provider, model, temperature }` with a **provenance badge per field** — `code default` · `area` · `call override` — plus any `rejected` / `locked` / `adjusted` issue attached to the field it affected. A header line states: *this is what is configured; running instances can lag by up to 60 seconds*. | G-1. An operator who reads a stored row believes an absent field means "nothing is set" when it means "the code default is in force", and believes a rejected field is in force when it is not. Provenance is the difference between "this area has no temperature" and "this area uses 0.3 from code". The script already prints all three; the screen must not print less |
| **D-3** | ✅ **Validation parity is achieved by calling `validateAreaRow`, not by restating its rules.** The route builds the candidate row and calls `validateAreaRow(area, candidate)`. Any `rejected` issue (guardrail, `locked`, `unknown`) **blocks the write**. `adjusted` issues are returned as warnings and do not block. Client-side checks are convenience only. A unit test asserts the route imports `validateAreaRow` and contains no re-implementation of a guardrail. **The validation is re-run at write time from the submitted row; the preview's verdict is never re-used (change 5).** | G-2. The script's strength is that it cannot drift from the resolver. SA confirmed the seam: `validateAreaRow` is a pure function of `(area, unknown)` using a **fresh** `newGuardrailContext()`, so a route call cannot poison the serving cache, and its cost is a memoised lookup over `getPricing`'s 1-hour module cache. SA's changes fix the two ways the panel as first written would have *created* false confidence — a call in flight at switch time lands in the ledger after it, and a quiet area renders the reassuring sentence while proving nothing |

A caveat placed *beside* a reassuring sentence loses to the reassuring sentence. | **D-6** | 🔄 **Every successful save writes exactly one audit entry, plus a second `critical` entry when an area is switched off (change 8).** `BOS_LLM_SETTINGS_UPDATED` — `entityType: 'settings'`, `entityId: 'bos_llm_area_<area>'`, `resourceName: '<Area> AI settings'`, `severity: 'warning'`, actor = the acting admin's user id, **`changes: { before, after }`** carrying both the raw row diff and the resolved-per-call diff. `BOS_LLM_AREA_DISABLED` — `severity: 'critical'`, **`details`** (matching the `logAIPricingZeroCost` precedent it cites), naming the area and any calls switched off with it. The value is looked up with `adminUserRepository.findByEmail`; an **active admin** yields that admin's `user_id`, which goes into both the audit entry and `updated_by`, so a script change is indistinguishable from a screen change in the trail. **When no actor is supplied, or it resolves to no active admin, the script does not invent one and does not stay silent:** it writes the audit entry with `userId: null`, `details.actorSource: 'break_glass_unattributed'`, the operator's optional `--reason`, and **`severity: 'critical'`** rather than `warning`; `updated_by` is left `null` (it is a user-id column, and a sentinel string would corrupt D-16); and the script prints a loud warn line. **Missing attribution never blocks the write.** | G-17: there is no session to read, so honesty has to be designed in. Making `--actor` *blocking* would mean the emergency tool refuses the emergency — the exact failure the break-glass door exists to prevent — so the cost of omitting it is a permanently louder, `critical`, explicitly-labelled record instead of a refusal. `--actor` plus an env fallback means an operator who sets it once in their shell profile is attributed for free, and the unattributed path stays available and obvious. **This is the part of BQ-4 that needs SA's eye (SA-10)** |

## What the Screen Shows

One page, eight area cards, one expanded at a time.

**Area card (collapsed):** area name · configured state (`Configured: on` / `Configured: off` / `Cannot be switched off`) · the area-level model · the number of calls with an override · **last changed by X at Y** (or *no stored row — running on code defaults*).

**Area card (expanded):**

| Section | Contents |
|---|---|
| **Area settings** | `enabled`, `provider`, `model`, `temperature` — each with its provenance badge and its lock state |
| **Calls** | One row per configurable call of the area (embeddings excluded, DEC-3). Resolved `enabled / provider / model / temperature`, each field badged `code default` · `area` · `call override`; locked fields disabled with their reason; any issue shown against the field it affected, with the guardrail's own reason string |
| **What "off" means here** | The owner-facing behaviour for this area, from the Layer 2 table — so an admin knows whether switching off degrades gracefully or shows a message |
| **Ledger check** | Per FR-18: window from save + 60 s, "calls **completed**", a before-change baseline, and one of three readings. **On chat this section is replaced by the D-5 statement** — the ledger cannot answer for chat |
| **Stored row** (collapsed) | The raw JSON, `updated_at` and **last changed by X at Y** (D-16). Read-only |

**Persistent, not dismissible, beside every switch:** *Switching an area off is not a guarantee. A settings-read failure on a newly started instance re-enables a switched-off area. Confirm at the ledger, not at this switch.*

**Not shown, deliberately:** any claim that a save is protected against a simultaneous save by another admin. There is none (D-10, withdrawn).

## User Stories

- As a **platform admin**, I want to see what model, provider and temperature every Business OS AI call is actually using — and where that value came from — so that I can change the right thing.
- As a **platform admin on call**, I want to switch a Business OS AI area off from my phone or laptop in under a minute, without a repository checkout or the service-role key, so that I can stop a cost runaway when I am not at my desk.
- As a **platform admin**, I want the screen to refuse exactly what the change script refuses, and tell me why in the same words, so that I never write a setting the system will quietly ignore.
- As a **platform admin**, I want to see the effect of my change *before* it is written, and then confirm it in one step that says what will happen, so that a mistyped override is caught by me and not by a customer.
- As a **platform admin who has just switched an area off**, I want to see whether calls have actually stopped — **and to be told when the evidence cannot answer that question** — so that I never walk away from an incident believing a switch that has not held.
- As **the other platform admin**, I want to be told when someone switches an AI area off, so that I am not debugging "why are insights suddenly generic" while my colleague already knows.
- As a **platform admin**, I want each area to show who last changed it and when, so that a value I did not expect has a name against it.
- As the **person responsible for the platform**, I want an AI area being switched off for every customer to be a deliberate act with a record — **including when it was done from the command line in an emergency**.

## Functional Requirements

### (a) Access and routes

1. **FR-1 — Admin only, by the one gate; the nearest neighbour is not the pattern (change 9).** The route's **first statement** is `await requireAdmin(requestLogger)`; nothing above it parses a body, reads the database or writes. 401 signed out, 403 non-admin. Never `profiles.role`, never a hand-rolled `AdminAccessService` call inside `route.ts`.
   - ⚠️ **The sibling `app/api/admin/business-os/llm-usage/route.ts:53-65` hand-rolls `AdminAccessService.getInstance().isAdmin(...)` inside `route.ts`.** It is one of the seven parked inline handlers, and **copying it fails the required `admin-authz-guard` check**. This route uses `requireAdmin`. Bringing the neighbour into line is not in scope here.
   - The page lives under `/admin` and is guarded by `app/admin/layout.tsx` inheritance — it adds no guard of its own. **There is no read-only view for non-admins** (D-7, BQ-3).
2. **FR-2 — A dedicated route with a typed area.** Indicative `app/api/admin/business-os/llm-settings/route.ts`:
   - `GET` — all eight areas: stored row, `updated_at`, **`updated_by` resolved to a label (FR-14)**, resolved settings per call with provenance, issues, lock metadata, allowed providers, temperature bounds, and the priced-model options (FR-8).
   - `PUT` — body `{ area, row, dryRun?: boolean }`. `area` is validated against `BOS_LLM_AREAS`; the storage key is derived server-side with `bosLlmAreaKey(area)`. **The client never supplies a key.** There is **no** concurrency token (D-10, withdrawn).
   - Zod validates the body before any business logic. `runtime = 'nodejs'`, `dynamic = 'force-dynamic'`.
   - **Literal-gate design constraint (change 11).** The route is inside `check:bos-llm-literals`, whose header names four shapes it cannot yet distinguish and prescribes the fix. The route is therefore designed to contain **no model-id union type, no `z.enum` of model ids, no `switch` on a model name, and no price-index key literal**: the area enum comes from `BOS_LLM_AREAS`, the model options come from pricing at request time (FR-8), and `TEMPERATURE_BOUNDS` already lives in the exempt policy module. **If one of the four becomes unavoidable, the fix is a narrow rule change in the gate with SA review — never a new file exemption.**
3. **FR-3 — The generic route's refusal is kept (D-1).** `PUT /api/admin/system-config` continues to return 400 for any canonicalised `bos_llm_area_*` key. Only its **message** changes, to name this screen instead of the script. The duplicated-prefix test that keeps the route and `modelSettingsPolicy` in step stays green.

### (b) Reading

4. **FR-4 — Resolved first, with provenance (D-2).** For every configurable call the response carries the resolved `{ enabled, provider, model, temperature }`, and for each of the four fields the level it came from (`call` · `area` · `default`). `temperature: undefined` renders as **"not set — the provider default applies"**, never as blank or `0`.
5. **FR-5 — Issues are surfaced against the field they affected.** Every `rejected`, `locked`, `unknown` and `adjusted` issue from `evaluateAreaRow` is returned with its `level`, `callName`, `field`, `kind`, `reason` and `value`, and the UI attaches it to that field. The guardrail's own `reason` string is shown, with a short plain-language gloss beside it.
6. **FR-6 — The client imports no server module.** Areas, call names, locks, switchability, allowed providers, temperature bounds and model options all arrive from `GET`. The `'use client'` page must not import `modelSettings`, `modelSettingsPolicy`, `modelSettingsSchema` or `callCatalog`, and must contain **no model name or temperature literal** of its own. Because the page imports nothing from the catalog it is outside both CI gates; a **source-level test** is the enforcement.
7. **FR-7 — Missing rows are shown as such.** An area with no stored row renders *no stored row — every call is running on its code default*, with the code defaults displayed normally and no "last changed by" line. This is not an error state.
8. **FR-8 — Model options are derived, never written down (change 6).** `GET` returns, per provider, the models with an active price whose input **and** output costs are both > 0, read at request time from the same pricing source the guardrail's `priceFor` uses. **No literal model array exists anywhere in this feature.** The list is labelled *advisory, refreshed hourly* and shows its cache age, because `getPricing`'s one-hour TTL means a newly priced model can be absent for up to an hour — which is why free text remains accepted and is validated identically. `validateAreaRow` is authoritative.

### (c) Writing

9. **FR-9 — One validator (D-3).** `PUT` constructs the candidate row and calls `validateAreaRow(area, candidate)`. Any `rejected` issue → **400, nothing written**, with the full issue list. `adjusted` issues → written, returned as warnings. No guardrail rule is restated in the route or the client.
10. **FR-10 — Preview is structural, and never the gate (change 5).** `dryRun: true` returns `{ ok, rejected, adjusted, resolvedBefore, resolvedAfter }` and writes nothing. The UI has **no** code path that reaches `dryRun: false` without having rendered that response to the admin. **The write path re-runs `validateAreaRow` from the submitted row immediately before the write; the preview's verdict is never cached or re-used** — prices and the image configuration can move between the two calls.
11. **FR-11 — The switch-off call-override trap (G-10).** When an area is switched off while one or more call entries hold `enabled: true`, the route refuses the write and names those calls. The UI then offers one explicit choice — *also switch these N calls off* — which re-submits with those entries set to `false` (the `--include-calls` equivalent). There is no silent resolution in either direction.
12. **FR-12 — Locked fields are disabled, with their reason (D-13).** Onboarding's area switch, the chat planner's switch and temperature, and the image call's temperature are rendered as disabled controls carrying the reason. The route still refuses a locked value if one arrives (FR-9 covers it) — the UI is a convenience, not the gate.
13. **FR-13 — The write records its actor (D-16; restores the original SA-4 proposal).** `SystemConfigRepository.set` gains an **optional actor** parameter which, when supplied, sets `updated_by` alongside `value` and `updated_at`. Existing callers that omit it behave exactly as today. The route passes the acting admin's user id; the script passes its resolved break-glass actor (FR-24). All writes go through the repository — no direct Supabase call in the route.
    - **There is no concurrency control** (D-10, withdrawn): no `setIfUnchanged`, no `expectedUpdatedAt`, no 409. Two simultaneous saves last-write-wins.
14. **FR-14 — "Last changed by X at Y" (D-16).** `GET` returns, per area, `updated_at` and a label for `updated_by`, resolved by matching the id against `adminUserRepository.listActive()`. An id that matches no active admin is rendered as the raw id, labelled unresolved — **never as "unknown" or blank**, which would read as "nobody". An area with no stored row shows no line (FR-7). The screen renders it on both the collapsed card and the "Stored row" panel.
15. **FR-15 — One confirm step, naming what will happen (D-8, BQ-1).** After the FR-10 preview, every write — a model, provider or temperature change, a switch-off and a switch-on alike — requires exactly **one** confirmation that states the action in plain words and names its reach, for example *"Switch insights AI off for all businesses?"* or *"Change the website model from gpt-4o to gpt-4o-mini for all businesses?"*. **No typed confirmation, and no second tier.** For a switch-off the confirmation also carries the fail-open sentence (FR-17) and, where it applies, the FR-11 choice. Confirmation is a UI requirement; the route never depends on it.

### (d) Honesty about "off"

16. **FR-16 — The screen never claims an area is off (D-4a).** The state chip reads **"Configured: off"**. No label anywhere on the page asserts that no calls are being made.
17. **FR-17 — The fail-open warning is standing and undismissible (D-4b).** One sentence beside every switch, stating that a settings-read failure on a newly started instance re-enables a switched-off area and that the switch is not a guarantee. It links to runbook §5, and it is repeated in the FR-15 switch-off confirmation.
    - ⚠️ **2026-09-24 — OPEN OBLIGATION ON SLICE 3, unchecked.** The refinements round ([BUSINESS_OS_LLM_ADMIN_SCREEN_REFINEMENTS_REQUIREMENT.md](/docs/requirements/BUSINESS_OS_LLM_ADMIN_SCREEN_REFINEMENTS_REQUIREMENT.md), FR-1/FR-5/FR-16) removed the on/off switch **surface** from the read-only page, so this obligation is currently **vacuous, not withdrawn**: there is no switch for a sentence to sit beside. What survives is one muted line in the page header (`PAGE_STANDING_NOTE`), which carries the residual non-switch truth and the runbook §5 pointer.
      - [ ] **Slice 3 restores the banner, the inline sentence and the FR-15 confirmation sentence in the same change that puts a control on the page.** This is recorded here, and not only in the `AreaCard.tsx` comment, because slice 3 is the change most likely to rewrite that comment (SA R-A condition 3 / refinements FR-16).
18. **FR-18 — Ledger check (D-4c; changes 2, 3, 4 and 10).** A read-only, refreshable panel per area, served through the repository layer — the route performs no direct Supabase query.
    - **Window (change 2).** The observation window starts at **the save timestamp + `BOS_LLM_SETTINGS_CACHE_MS` (60 s)**, never at the save itself. `token_usage` is written by `callWithTracking` **after** the provider call resolves, so a call that began before the switch lands in the ledger after it.
    - **Wording (change 2).** "No calls **completed** since X" — not "no calls observed". The panel also states that a `token_usage` insert failure is **logged and swallowed**, so an under-count is silent: this check is **corroboration, not proof**.
    - **Baseline and three readings (change 3).** The panel also reads the **same-length window immediately before the change** (or the area's last call time). It then renders exactly one of:
      1. *Calls are still arriving — the switch is not holding on every instance.*
      2. *No calls completed since X, and this area was making calls before the change.* (the only reading that corroborates the switch)
      3. *This area had no traffic before the change either — the ledger cannot tell you whether the switch is holding.* (**required**: `briefing` is daily, `insights` is cron-driven and `onboarding` is sporadic; without this branch the panel renders reading 2 on exactly the areas where it proves least)
    - **Data (change 10).** A **new, explicitly named cross-tenant aggregate** on the usage repository, following the `listChatCallsAllAccountsInWindow` precedent: e.g. `…AllAccountsInWindow`, returning **count, latest timestamp and cost sum only** — no per-account breakdown, no owner text. The `feature` value is derived server-side from `bosFeature(area)` and is never caller-supplied. Admin-only, read-only. **This is a deliberate cross-tenant read**, recorded as such because every other read in that repository takes `userIds` and runs `assertAccounts`: the question "is this platform-wide switch holding" has no per-tenant answer, and an aggregate of three numbers exposes no tenant data.
    - The panel never states that an area is off.
19. **FR-19 — On chat the panel is context, not evidence (D-5, change 4).** The chat card **does not render readings 1–3**. It states that the ledger cannot answer for chat, because `AIDataLayerService` writes no `token_usage` row, and names the entry gate and the resolver's `Business OS LLM settings changed` server log as the only available checks.
20. **FR-20 — Propagation is stated.** After a successful write the screen states that running instances pick the change up within about 60 seconds, and that the ledger check only begins counting after that (FR-18).

### (e) Audit, notification and logging

21. **FR-21 — One audit entry per successful save (D-6, change 8).** `BOS_LLM_SETTINGS_UPDATED`, **`entityType: 'settings'`**, `entityId: 'bos_llm_area_<area>'`, `resourceName: '<Area> AI settings'`, `severity: 'warning'`, actor = the acting admin's user id, **`changes: { before, after }`** carrying both the row diff and the resolved-per-call diff. Non-blocking (`.catch()`).
22. **FR-22 — A second `critical` entry when an area is switched off (change 8).** `BOS_LLM_AREA_DISABLED`, `severity: 'critical'`, carrying **`details`** (matching `logAIPricingZeroCost`) that name the area and any calls switched off with it. Written **in addition** to FR-21. A switch back on writes FR-21 only.
23. **FR-23 — Both events are registered (change 8).** Each new event gets a row in the metadata registry in `lib/audit/events.ts` (~:725 onwards) with its severity, `complianceFlags: ['SOC2']` and a description, alongside its helper pair in `lib/audit/admin-helpers.ts`. The helpers are used by **both** doors.
24. **FR-24 — The break-glass door writes the same entries, with an honest actor (D-18, BQ-4).** `bos:llm-settings set` writes FR-21 and, on a switch-off, FR-22.
    - **Actor resolution order:** `--actor <email>`, else `process.env.BOS_LLM_SETTINGS_ACTOR`. The value is resolved with `adminUserRepository.findByEmail`; an **active admin** yields that admin's `user_id`, used for the audit entry **and** passed to `set` as the FR-13 actor, so `updated_by` is populated exactly as a screen save would and FR-14 shows the same name.
    - **When no actor is supplied, or it resolves to no active admin:** the entry is still written, with `userId: null`, `details.actorSource: 'break_glass_unattributed'`, the operator's optional `--reason` if given, and **`severity: 'critical'`** instead of `warning`. `updated_by` is left `null` — it is a user-id column, and a sentinel string would corrupt FR-14. The script prints a loud warn line naming the area and the missing attribution.
    - **Missing attribution never blocks the write.** An emergency tool that refuses an emergency is the failure this door exists to prevent.
    - `get`, `verify-stored` and `verify-equivalence` are read-only and write no audit entry.
25. **FR-25 — Notify the other admins on switch-off (D-17, BQ-2).** When a save switches an area off — **only** then; not a model, provider or temperature change, and **not** a switch-on:
    - Recipients are `adminUserRepository.listActive()` **minus the acting admin**; if that list is empty, nothing is sent and an info line records why.
    - The message is sent with `sendEmail` (`lib/notifications/emailTransport.ts`) and names the area, who switched it off, when, and one line that the switch fails open. It contains no owner data and no prompt text.
    - **Non-blocking**: a notification failure never fails the save, exactly like the audit write.
    - **`sendEmail` returns `{ sent: false, provider: 'none' }` when no transport is configured rather than throwing.** That result is logged at **`warn`** with the recipient count and the provider — a notification nobody received must not be recorded as one that was sent.
    - The break-glass script sends the same notification when it switches an area off.
26. **FR-26 — Refusals are logged, not audited.** A refused save (400) logs at warn with `userId`, `area` and the reasons, and writes no audit entry and no notification.
27. **FR-27 — Pino only, with `correlationId`.** No `console.*` in any file this layer touches; any that is touched and non-compliant is flagged and converted per CLAUDE.md. No prompt or owner text is ever logged — these settings contain none.

## Non-Functional Requirements

- **Security:** admin-only by `requireAdmin` (route) and `requireAdminPage` inheritance (page); no read-only tier (D-7). No service-role key leaves the server. The client cannot name a settings key. No `error.message` reaches the client outside development. The notification is sent only to addresses from `admin_users`, never to an address from a request.
- **Tenant isolation:** exactly **one** deliberate cross-tenant read exists in this feature — the FR-18 aggregate — explicitly named `…AllAccountsInWindow`, returning three numbers, deriving its `feature` from `bosFeature(area)`, admin-only. `adminUserRepository.listActive()` is an existing admin-only read used for its documented purpose. No other unscoped read is introduced.
- **Concurrency (stated absence):** **none.** Two simultaneous saves of the same area silently last-write-wins (D-10, withdrawn by the user). FR-14 makes the overwrite visible afterwards; nothing prevents it. Re-introducing a guard is a requirement change.
- **Reliability:** the screen can never make Business OS worse than it is. A failed read renders an error state; it does not write. A failed write writes nothing. Neither the audit write nor the notification can fail a save.
- **Correctness:** exactly one validator (`validateAreaRow`) and one resolution implementation (`evaluateAreaRow`) for both doors; the write-time validation is re-run, never re-used from the preview (FR-10).
- **Repository pattern:** all reads and writes through `SystemConfigRepository` (`set` with the new optional actor, the area-row read), the usage repository (the FR-18 aggregate) and `AdminUserRepository` (`listActive`, `findByEmail`). No direct Supabase call in the route, the page or the script.
- **Type safety:** the route is inside `typecheck:bos-llm` and `check:bos-llm-literals` and must avoid the gate's four known false-positive shapes by design (FR-2). 0 new diagnostics, baseline unchanged, **no new file exemption**. The client page is outside both gates, which is why FR-6 is enforced by a source test.
- **Performance:** one `GET` builds the whole page, including "last changed by" (the row already carries it; `listActive()` is one small admin-only query). The ledger check is a separate, explicitly-triggered request issuing two bounded aggregates. No polling.
- **Accessibility:** every control reachable and operable by keyboard; lock reasons, issue text, the confirmation sentence and all three ledger readings are real text, not tooltip-only; the state chip is not colour-alone (`Configured: off` is words).
- **Logging:** Pino with `correlationId` on the route; no `console.*`. A non-delivered notification is logged at `warn` (FR-25).
- **Testability:** the route is testable with the repositories, `validateAreaRow`, the audit service and `sendEmail` mocked. The confirmation step and the three ledger readings are component-testable. The script's actor resolution is unit-testable without a database.

### Required changes

1. **(D-10 / FR-14 / SA-5 — blocking) The 409 must be a write predicate, not a prior check.** `SystemConfigRepository.set` (`lib/repositories/SystemConfigRepository.ts:259-312`) is **read-then-write**: `getByKey`, then `.update({ value, updated_at }).eq('key', key)`. Comparing `basedOnRowUpdatedAt` in the route and *then* calling `set()` is check-then-act — two admins can both pass the check and both write, which is precisely the last-write-wins D-10 exists to prevent. Replace FR-13's "optional actor on `set`" with a **new method**, e.g. `setIfUnchanged(key, value, expectedUpdatedAt, actorId)`, that carries the compare **in the statement** — `.update({ value, updated_at, updated_by }).eq('key', key).eq('updated_at', expectedUpdatedAt).select()` — and treats **zero rows returned** as the 409. `set()` is left alone, so the script and the Step 0 route are undisturbed (SA-4 answered). For an area with **no** stored row, `basedOnRowUpdatedAt: null` must take a conditional insert, and a unique-key violation must map to **409, not 500**. Before relying on `updated_at` as the token, Dev must confirm from the table's migration that no DB trigger also writes it — the update sets it in application code, and a trigger writing a different value would make the read-back token stale on the very next save. AC-14 must assert the race, not just the stale-token case.
2. **(D-4c / FR-18) The ledger window must start after propagation, and the wording must say *completed*.** The row is written by `callWithTracking` (`lib/ai/providers/baseProvider.ts:77`) **after** `apiCall()` resolves, via a synchronous `token_usage` insert (`lib/analytics/aiAnalytics.ts` ~:210). So a `website/full_site` call that started before the switch lands in the ledger after it, and a failed insert is **logged and swallowed**, never thrown — an under-count is silent. ### Must-fix

1. **R-1 (correctness — D-18 / FR-24 and D-16 / FR-14) `admin_users.user_id` is nullable, and both new lookups assume it is not.** `AdminUserRepository.ts:27` states it plainly: *"null until the admin has an auth account, then bound"*, and `findByEmail` (`:88-103`) filters on `is_active` only — so it can return an **active admin with `user_id: null`**.    - FR-24's "an active admin yields that admin's `user_id`" then takes the **attributed** branch and writes `userId: null` with no `actorSource` label — an entry that claims attribution and carries none, at `warning` rather than `critical`.
