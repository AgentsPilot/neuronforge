## Overview

Layers 1, 1.1, 1.5, 2 and 3 of the Business OS LLM work made every Business OS AI call **recorded**: attributed to the right business, catalogued with an area and a call name, grouped by the action that caused it, cost-tracked in the usage ledger (`token_usage`), model-configured from the database, and summarised into one audit entry per AI action. The user then asked the obvious next question: **"is there a view page where an admin can see these calls?"**

The answer today is *partially*. The data is all there and an admin can reach it — but only through three screens that were each built for a different job, and never in one place that answers "what did this business's AI do, did it work, and what did it cost?". This requirement covers two related gaps:

- **Gap A — AI actions can be seen but not filtered.** Business OS AI audit entries land in the existing `/admin/audit-trail` page and their details are readable, but the page's Action and Entity Type dropdowns are hardcoded lists that were never extended, so there is no way to isolate AI activity from every other audited event.
- **Gap B — the two halves of the record are never joined.** The audit entry says *what the product did and whether it worked*; the ledger rows say *what each underlying call cost*. No screen puts them together, so an admin cannot click one AI action and see the calls behind it, or go the other way.

This requirement is **read-only operator visibility**. It changes nothing about what is recorded, attributed, charged or configured. ~~It does, however, need **one database migration** — a grouping query the ledger cannot answer today (F-14) — which is now its own first slice.~~ **Re-plan 2026-10-02:** no grouping query and no SQL function are needed. The credit-deduction work now writes **one charge row per AI action** (F-19), which is the row this view lists; the list is a plain filtered read of that table. It does need **one small index migration on that table, planned as slice B0′** (SA-RC-1). *(Superseded wording, 2026-10-02: "with at most one supporting index if a measurement shows it is needed (B0′, pending SA)".)*

## User Stories

- As a **platform admin**, I want to filter the audit trail to Business OS AI actions, so that I can see AI activity without scrolling past every other audited event.
- As a **platform admin**, I want the audit trail's filters to keep working when we add new event types, so that this gap does not come back every release.
- As a **platform admin investigating one business**, I want a list of the AI actions that ran for it — what the product was doing, whether it succeeded, and what it cost — so that I can explain a failure or a bill without running a database query.
- As a **platform admin**, I want to open one AI action and see the individual AI calls it made, so that I can tell an expensive run from a chatty one.
- As a **platform admin doing a cost sweep**, I want to sort or filter AI actions by cost and by outcome across all businesses in a window, so that I can find the outliers and the failures without knowing where to look first.
- As a **platform admin**, I want to be told when an action's recorded cost and the sum of its underlying calls disagree, so that I do not quote a number that is wrong.
- As a **platform admin**, I want a row to contain **only** the business it belongs to, so that a number I quote to one customer never includes another customer's spend.
- As a **platform admin**, I want spend that has no action record, no group or no real account to be **shown and labelled** rather than dropped or lumped together, so that the screen's totals are the truth and the "we lost an entry" number means something.
- As a **platform admin**, *(added 2026-10-02)* I want each action's row to show what we **charged** for it and whether that charge was priced from a fallback rate or later corrected, so that the activity screen and the bill never tell two different stories.
- As a **compliance reviewer**, I want this view to show identifiers, counts, labels and numbers only — never a prompt, an owner's words, the model's output or an error message — so that an operator screen does not become a second copy of business content.
- As a **business owner**, I want nothing about this to make my own AI activity or cost visible to me yet, or to anyone outside the platform team.

### D-1 — The ledger is the money number, and a disagreement marks the row

*(was OQ-1; first half ruled by SA, second half answered by the user)*

**Settled, not a fork:** the **ledger is the money record**. Layers 1 and 1.5 already established that — owner usage and any future charging are built on `token_usage` — so the audit entry's `estimatedCostUsd` is the "what happened" number and never the authoritative one.

**The user's answer to the rest:** when the two disagree, **mark the row and show both numbers**. Do not average, do not silently prefer one, do not hide the other.

**Tolerance: $0.0001** (one ten-thousandth of a dollar), i.e. just above the rounding floor. `buildAiAuditEntry` rounds its sum to a **micro-dollar** (`aiActionAudit.ts:198-199`) while the ledger sums per-row values, so sub-micro-dollar drift is arithmetic noise and nothing else. A threshold at $0.0001 sits two orders of magnitude above that floor — comfortably clear of false positives, and far below any real loss.

**Why this matters more than it looks (F-17):** both numbers are computed from the *same* in-memory `UsageCallRecord` objects. The arithmetic **cannot** disagree. A mismatch beyond rounding therefore always means one of the two independent writes failed or was diverted — `trackAICall` logs and swallows every ledger insert failure (`aiAnalytics.ts:215-226`), a non-UUID `session_id` is nulled (`:140-146`), an invalid `user_id` is diverted to the platform account (`:131-137`). **The mismatch marker is the only self-check the attribution instrumentation has.** That is the reason to build it, and the reason a generous tolerance would defeat the purpose.

**Re-based 2026-10-02 — ruled by SA the same day (SA-R2, SA-R3).** The precedent the first half rested on has moved. The deduction layer made **`business_os_credit_charges` the bill** and `token_usage` the per-call detail and safety net (F-19). So, per action row: **the authoritative figure is the charge row's `cost_usd`, net of any adjustment rows that point at it** (FR-B12), and credits likewise. `token_usage` is the drill-down and the cross-check; the audit entry stays the "what happened" number. The column is labelled **"Cost (USD)"**, not "Charged cost": owners are charged **credits**, and `cost_usd` is our cost basis (SA-R2). **The user's answer is unchanged**: where the cross-checks disagree, mark the row and show both numbers. **Two tolerances (SA-R3):** the charge-vs-entry check stays at the user's **$0.0001** — both sides are 10-decimal sums of the same records, so any difference is a writer defect; the group-level check against `token_usage` uses the leak check's exported `leakTolerance(calls)` (one micro-dollar per call), which **applies this decision's own rationale** — a threshold just above the rounding floor — to a source whose floor is now one micro-dollar per call (F-23), so the view and the leak check can never classify one group differently. FR-B6 says which numbers are compared and where. **A fallback-priced charge is not a disagreement**: it is shown with its own marker (F-23, FR-B6). *(Superseded wording, 2026-10-02: "BA proposal, for SA — SA-R2 … Whether the group-level comparison should use the leak check's per-call tolerance instead, so the two screens can never disagree, is SA-R3.")*

### What one row is

**One row = one charge row** of `business_os_credit_charges` with `kind = 'charge'` — one `runAiAction` invocation — whose `created_at` falls in the window. Adjustment rows are **never** rows of their own; they are netted into the charge they adjust (FR-B12).

| Rule | Statement |
|---|---|
| **Row key** | `action_id` — UNIQUE on the table (`20261015:26`). The row's account is the charge's `user_id`, written server-side by `runAiAction` |
| **Audit join** | Through a new **named cross-account** method on `AuditTrailRepository` (NFR-4.4) that takes the ≤ 100 rows' group ids and filters `entity_type = 'ai_action'`, `action IN (BUSINESS_AI_ACTION_COMPLETED, BUSINESS_AI_ACTION_FAILED)` and `entity_id IN (…)` (served by `idx_audit_trail_entity_id`, live state per SA-RC-9) — **never by severity**, which is decided at write or registration and is not an outcome signal. Entries of another account that share a client-header group (F-28) are fetched but **discarded server-side and never serialised**; an entry that matches on `actionId` but not on account is a **defect marker**, never shown as either account's data. Only `schema: 2` entries carry `actionId` (F-22). JSONB containment is not used (SA-R6, SA-RC-12). **Case (added 2026-10-02 per the B1 workplan's SA review, OQ-6):** `audit_trail.entity_id` is `text` and keeps the case of a client-supplied id — chat-v4 passes the client's turn id through unchanged — while the charge's `group_id` is a `uuid` and reads back lower-case. | **Drill-down** | `token_usage` filtered on `session_id = group_id` **AND** `user_id = charge.user_id` — **never the group id alone** (F-13, F-28). The drill-down request carries **only the action id**; group and account are read from the charge row, never from the request (FR-B2, SA-RC-11) |

### FR-B6 — Reconcile the two cost numbers

*(Rewritten 2026-10-02 — D-1 re-based; ruled by SA the same day: SA-R2, SA-R3, SA-RC-4.)*

**The money figure per row is the charge's `cost_usd`, net of adjustments.** Two cross-checks run against it, and each one, when it fails, **marks the row and shows both numbers** ([D-1](#decisions)):

1. **Charge vs. audit entry — on the list, at $0.0001.** Both are built from the same in-memory calls and both are stored at 10 decimals (F-20, F-23), so they must be equal — **except** on a fallback-priced charge, where the entry records $0 for the unpriced call and the charge records the conservative fallback. A mismatch on a charge that is **not** fallback-priced is a defect in one of the two writers. This is the **only** cross-check that runs on the 100-row list.
2. **The group's charges vs. the group's `token_usage` — in the drill-down only, at the leak check's tolerance.** The sum of every charge row in the group (net of adjustments) is compared with the sum of the group's calls, by account — never one charge against a shared group's total, which would mark every multi-action group by construction (the SA re-check §4 Q1 lesson, carried over). This catches a failed `token_usage` insert or calls outside the action. It **calls the exported `leakTolerance(calls)`** (`creditLeakCheck.ts:114`, one micro-dollar per call) and nets adjustments exactly as `classifyLeakGroups` does, so the view and the leak check can never classify one group differently (SA-R3). It runs in the drill-down (one account, one group, FR-B2) and, for a single business, through the leak check (FR-B5 question 2) — **never on the 100-row list, which does not read `token_usage`** (SA-RC-4).

**Fallback-priced charges are not mismatches.** They carry their own marker — "priced from a fallback rate, pending reconciliation" — with the direction against `token_usage` (over, the expected case; or under), exactly as the leak check reports them. Once reconciled, the row shows the original and the corrected figure (FR-B12).

### FR-B8 — Ungrouped, platform-account and deleted-account spend get labelled buckets

*(Updated 2026-10-02 per SA-RC-3 and SA-RC-10.)*

Business OS spend legitimately exists with **no group** and with **no real account** (F-16), and charge rows can lose their account when it is deleted (F-24). A ledger-first view would either drop them silently or collapse them into one nonsense row. Neither is acceptable:

- **Ungrouped spend** (`session_id IS NULL`) is the leak check's **ungrouped calls** class, with the chat v1 intent parser on its own **known uncharged path** line (F-27). For a single business and ≤ 7 days it is shown inline from the existing leak-check route; otherwise it is reached by link (FR-B5 question 2).
- **Platform-account rows** are the leak check's **all-accounts platform-account figure** — **counts only, no dollar total** (F-26) — reached by link to the Costs & credits tab. A platform row belongs to no business, so it **never appears in single-business mode**. These are rows where attribution failed and the tracker fell back to the platform account (`aiAnalytics.ts:131-137`); the view never hides that figure, because it is exactly the failure Layer 1 exists to catch.
- **Charges whose account was deleted** (`user_id` NULL, F-24) are the view's **own** bucket, read through a purpose-named method on `BusinessOsCreditLedgerReadRepository`: `.is('user_id', null)`, `kind = 'charge'`, the window. Its count is `count: 'exact'`. Its **total cannot be a database `SUM`** (PostgREST aggregates are disabled, F-14): it is summed in Node from a ceiling-bounded page, with adjustments netted, and shown as **"at least"** when the ceiling is reached. These rows are never mixed into any business's figures (SA-R12, SA-RC-10).

All three state plainly that they are *not* audit loss (FR-B5). The first two come from `token_usage` through the leak check (they never have a charge, F-20); the third from the charge table.

### FR-B9 — The reverse pass: audited but not charged

*(Re-based 2026-10-02; bounded per SA-RC-5.)* Charge-first fixes one blind spot and opens another: an action whose **charge write failed**, timed out with an unknown fate, or was **skipped** (`unpriceable`, `not_charged`) has an audit entry but no charge row (F-20, F-27), and is invisible to a charge-first list.

**For a single business** and the bounded window, the view therefore runs a reverse pass: that business's `schema: 2` AI entries in the window, up to a ceiling, with each entry's `actionId` looked up through the **existing** `findChargesByActionIds` (`BusinessOsCreditLedgerReadRepository.ts:422` — by unique id; the caller checks that the charge's account is the entry's). An entry whose `actionId` has no charge is surfaced as an **"audited, not charged"** row with the entry's fields (and, where present, its `token_usage` calls by group and account). Rules:

- matching is by `actionId` **across all time**, never by window, because a charge and its entry can straddle a window edge;
- entries **before the cut-over instant** (F-21, SA-RC-9) and inside a short settle margin are excluded;
- when the ceiling is reached the section is flagged **"may be incomplete"**;
- the label claims **no cause** — a failed write, a timeout, `unpriceable` and `not_charged` all land here.

**Across all accounts the reverse pass does not run.** Reading every AI entry in a cross-account window is about 116,000 entries a month at the NFR-6 design figure — F-5's "page everything into Node" defect again. There the view relies on the leak check (FR-B5 question 2) and on the `bos_ai_charge_write_failed` / `bos_ai_charge_not_written` error logs.

This is the deduction layer's FR-16 failure, seen from the audit side; the leak check sees the same action from the `token_usage` side. *(Superseded 2026-10-02 (SA-RC-5): "The view therefore runs a **second, cheap pass**: `schema: 2` AI entries in the window whose `actionId` has **no charge row** …", unbounded and across all accounts. ### FR-B11 — The read is answered in the database

*(Rewritten 2026-10-02; ruled by SA the same day — SA-R1, SA-R5, SA-RC-1, SA-RC-2, SA-RC-4.)*

**The list needs no new SQL function.** Each row is one charge row, so the list is a filter, a sort, a 100-row limit and an exact count over `business_os_credit_charges` — none of which is an aggregate, so PostgREST's disabled aggregates (F-14) do not apply. Specifically:

- **Through a repository — two named methods over one builder.** On `BusinessOsCreditLedgerReadRepository` (F-25): one **`…AllAccounts…`** method and one **account-scoped** method, over **one private builder**, the way `pageTotals` serves both totals reads (`:258-273`). **Not** one method with an optional account: that breaks the repository's own convention that all-accounts is a differently *named* method, never an omitted argument (`:30-36`). The builder: `kind = 'charge'` (allowed); a half-open `created_at` window; `action_type IN (…)` (the area's action types, passed in as plain data), `outcome`, `triggered_by` and `cost_usd >=` filters; order by `created_at` or `cost_usd`, with an `id` tie-break; the limit **asserted 1–100 in the repository and applied in the query**; `count: 'exact'` on the identical filters (not an aggregate); the existing column allow-list; **never** a filter or grouping on the raw `service` column — rows show the effective service. The all-accounts method writes an **`info` log**. The file header, which today says the totals read is its only cross-account read, is **amended in the same commit** (NFR-4.5).
- **Indexes — B0′, planned (SA-RC-1).** The 20261015 indexes do not lead with `created_at` and do not cover `adjusts_action_id` (F-24). B0′ is **one migration with no function**: (a) an index serving the cross-account `created_at` window, the order and the exact count — its shape is the workplan's, e.g. `(created_at DESC)`, optionally partial on `kind = 'charge'`; (b) a **partial index on `adjusts_action_id WHERE adjusts_action_id IS NOT NULL`**, for FR-B12's per-page adjustment lookup, which has no index today. It is **planned, not conditional**: at today's few thousand rows Postgres seq-scans whatever indexes exist, so a measurement cannot show a need that only appears at the design volume (NFR-6). The table's **live** `pg_indexes` is read before the migration is written (F-24, SA-RC-9). It is applied by hand on production, as a checkpoint **before** B1 is verified ([D-7](#decisions)), and evidenced by AC-B16.
- **What still needs arithmetic, and where it runs.** Netting adjustments (FR-B12) and the charge-vs-entry check (FR-B6 item 1) are computed over **at most 100 rows plus their own adjustments and entries** — bounded by the cap. **The list never reads `token_usage`** (SA-RC-4): the group-level check (FR-B6 item 2) runs in the drill-down, and the "no charge" figures and the ungrouped and platform-account buckets come from the leak-check route (FR-B5, FR-B8). The deleted-account total is a bounded Node sum (FR-B8). Window-level totals per business are **not** recomputed here: they come from the Costs & credits report (D-5 note, SA-R4).
- **Still rejected:** paging every `token_usage` row in a cross-account window into Node to sum it there — F-5's defect, which the usage-summary migration exists to undo.

### FR-B12 — Adjustments are netted into the charge they correct

*(Added 2026-10-02.)*

An adjustment row (`kind = 'adjustment'`) has no `action_id` of its own and points at the charge it corrects through `adjusts_action_id`; it carries a reason code and signed credits and cost, and no service, action type, trigger or outcome (`20261015:30`, `:36`). Therefore:

- An adjustment is **never a list row**. A row's cost and credits are the charge's **plus every adjustment that points at it**, whenever that adjustment was written — even in a later window or billing period. The per-page lookup of adjustments by `adjusts_action_id` is served by B0′'s partial index (FR-B11).
- A corrected row shows **both** the original and the net figure, and the reason code; the drill-down lists each adjustment.
- An adjustment inherits its charge's service, action type, area and trigger (deduction N-10, F-25). The view never filters on the raw `service` column.
- **Sorting a corrected row (SA-R8):** the cost sort and the minimum-cost filter use the **gross** charge cost in the query; the row **displays net** and is marked corrected. This is valid because slice 4c's planned bounds only let an adjustment **lower** a charge (slice 4 workplan `:287`), so gross ≥ net. If 4c ever allows a positive adjustment this ruling is revisited, and the B1 workplan records that dependency.
- **Today no adjustment can exist**: the only write function hard-codes `kind = 'charge'` (`20261015:219-227`) and the adjustment function is slice 4c, not yet built (F-24). The view is nevertheless built to be correct when 4c ships; a seeded test proves it (AC-B19). *(Superseded 2026-10-02: "How the sort by cost treats a corrected row is SA-R8.")*

## Non-Functional Requirements

These carry forward from the attribution work and are **non-negotiable**.

1. **NFR-1 — Admin-only, gated in the route, fails closed.** Every new or changed API route gates itself before reading anything: 401 signed out → 403 not an admin → 400 invalid input, with an admin check that throws treated as "no". Identity comes from the `admin_users` source of truth — **`requireAdmin` as the first statement** in any new route, `requireAdminPage` / the admin layout for pages. **Never `profiles.role`, never `app_metadata.role`, never a hand-rolled `AdminAccessService` call inside a `route.ts`** (that fails the CI guard). See [ADMIN_IDENTIFICATION_AND_ACCESS.md](/docs/admin/ADMIN_IDENTIFICATION_AND_ACCESS.md).
   - Converting the **existing** audit-trail handler is an explicit non-goal — see FR-A8.
2. **NFR-2 — Cross-account reads are deliberate, and limited to metadata. *(Scoped to the new Gap B view.)*** This view deliberately reads across accounts. It must therefore read and display **identifiers, company names, counts, labels, models, timestamps and numbers only** — **never prompts, request or response payloads, owner-entered text, AI output, error message bodies, or email addresses**. Only allow-listed columns are selected. The posture is already set out well in the header of `app/api/admin/business-os/llm-usage/route.ts:1-22` and in `lib/repositories/TokenUsageRepository.ts:24-26`; this view follows them.
   - **Identification** is account id + company name via `BusinessProfileRepository`, never email, and never a business name in a log line ([D-4](#decisions)).
   - **Cross-account *cost* mixing is part of this rule, not only a correctness concern.** A row that contains another business's spend (F-13) is the same class of mistake as a row that contains another business's text. The row key is `(session_id, user_id)`; a join on the group id alone is a privacy defect. *(Re-plan 2026-10-02: the list's row key is now `action_id`, which belongs to exactly one account; every read of `token_usage` and every audit join stays keyed on the group id **and** the account — F-28. Per SA-R5, the live risk is not RLS but a request-supplied account or group steering a second read to another tenant's rows, so: the drill-down takes only an action id and reads group and account from the charge row (SA-RC-11); and audit entries of another account that share a group are discarded server-side and never serialised (SA-RC-12).)*
   - **Scope note (SA-10).** This clause governs the **new Gap B view**. It does **not** apply retroactively to `/admin/audit-trail`, which already joins the `users` table and returns `email` and `full_name` (`audit-trail/route.ts:153-167`) and renders the email as each row's primary identifier (`page.tsx:533, 568`). That display is **pre-existing, out of scope and unchanged**; a compliance browser needs it. On the audit page the privacy rule applies **only to the new AI detail renderer** (FR-A5), where the closed `AiAuditDetails` shape makes it genuinely checkable.
3. **NFR-3 — Read-only, and no AI.** No writes (other than an admin service's own bookkeeping), no LLM calls, no embeddings, no audit event written by the view itself. ### Ruling 1 — The ledger-first axis is CORRECT, but the key is not the grouping id

### 2. Ruling on BA's extension 1 (no-call actions cannot distort the count) — **CONFIRMED**

BA is right, and the reasoning is sound. Verified end-to-end:

- `runAiAction` → `emitAiAuditEntry` returns early when `calls.length === 0` (`aiActionAudit.ts:304`), so an action that called nothing writes no entry — and it also wrote no ledger row, because a ledger row is only written by `trackAICall` from inside a call. In a **ledger-first** list it is not merely benign, it is **absent**. It cannot be in the denominator.
- The cache row is genuinely the exception: `recordCachedTurn` (`lib/business-os/bizql/telemetry/turnUsage.ts:85`) calls `trackAICall` **directly**, outside the usage scope, with `provider: 'cache'`, zero tokens and zero cost — and it early-returns unless the turn id is a UUID (`:88-94`), so such a row always *has* a group. That is precisely the shape that would have been read as audit loss.

FR-B5 and F-15 may stand as written on this point. The refinement is worth the words it takes.

### 3. Ruling on BA's extension 2 (the fourth cause) — **CONFIRMED, with one correction**

**The finding is correct and was missed on SA's first pass.** Verified: `validateIdentities` (`aiActionAudit.ts:252-258`) returns `null` when `!isUuid(spec.groupId) || !isUuid(accountId) || isPlatformAccount(accountId)`, and `emitAiAuditEntry` then writes nothing (`:306-310`). So:

- a **platform-account** ledger row is **permanently unauditable by design**, not lost — SA-4's bucket and SA-3's benign class really are the same rows;
- a **non-UUID grouping id** is refused by `validateIdentities` *and* nulled by the tracker (`aiAnalytics.ts:140-146`), so it lands in FR-B8's ungrouped bucket on the other side.

FR-B5 and FR-B8 agreeing with each other on that basis is correct.

**The correction — there is a fifth cause, and it lands in the residual bucket.** The audit account and the ledger account are **two independent parameters**, not one value: the ledger's `user_id` comes from `attribution.userId` through `buildBosCallContext` (`callCatalog.ts:283`, `:302`), while the entry's account comes from `spec.accountId` or `handle.setAccount`. `AiActionHandle.setAccount` exists **precisely because the account is sometimes discovered mid-action** (`aiActionAudit.ts:96-97`; exercised at `lib/business-os/llm/__tests__/aiActionAudit.test.ts:238`). If an action's calls carry a valid account but the spec's account is never set — or is set late, after a throw — the ledger rows have a **real `user_id` and a real `session_id`** and **no entry is written**. Nothing was lost; the write was refused.

That group is indistinguishable, *from the data*, from a genuinely lost entry. Two consequences, both for the **B1 workplan**, neither blocking:

1. **Rename FR-B5's residual class.** "Genuine loss or delay" overclaims. Call it **"No entry found — lost, delayed, or refused at write time"**, and state plainly that the view cannot separate a refusal from a loss. AC-B6's recorded figure is then honestly **an upper bound on KI-B** — still the first defensible measurement we have ever had, and a far better thing to publish than a number that quietly includes instrumentation bugs.
2. **The refusals are recoverable from the logs, cheaply.** Every refusal writes one error line — `AI audit entry not written: invalid grouping id or account, or the platform account` (`aiActionAudit.ts:308`) — carrying area, actionType, groupId and accountId. If B1's QA step counts those lines for the measured window, the residual can be split and KI-B becomes exact. Record as a **note in B1's QA procedure**, not as a functional requirement: the screen must not start reading logs.

### 4. Answers to BA's four queued questions

**Q1 — Briefing same-day re-narration: one row or split? → One row, as written. Confirmed.**

The ledger cannot attribute a call to one of the two entries: both entries share `entity_id` *and* `user_id`, and `token_usage` carries no discriminator that would separate run 1's rows from run 2's. Splitting would therefore require **inventing an allocation** (by timestamp, most likely) and presenting a guess as a fact. "Newest entry supplies the action fields, every entry listed in the drill-down, the row marked as carrying more than one" is the honest presentation, and it is what the data supports.

**But one thing must change in FR-B6, or this decision creates a permanent false-positive generator.** Where a group carries more than one entry, the cost reconciliation must compare the ledger sum against the **sum of every entry's `estimatedCostUsd`**, never the newest entry's alone. The ledger holds both runs' calls; the newest entry holds only its own. Compared against the newest alone, **every** multi-entry briefing group marks as a mismatch — by construction, forever — which would discredit the one self-check the attribution instrumentation has (D-1, F-17). Add that sentence to FR-B6 and an assertion to AC-B7.

**Q2 — Does FR-B5's classification match SA-3's intent? → Yes**, including both of BA's extensions, subject only to the residual-class rename in §3. The table is better than what SA asked for: SA asked for the benign causes to be separated, BA separated them *and* tied each one to a self-identifying marker in the data. The trailing-exclusion-window row is the part SA would have forgotten.

**Q3 — Should FR-B11 pin the function signature and index columns? → No. Leave them to the B0 workplan.**

FR-B11 already pins everything that is **non-negotiable**: INVOKER rights, `REVOKE ALL ... FROM PUBLIC, anon, authenticated`, grouping by `(session_id, user_id)`, the window + Business OS feature prefix as the access path, the limit applied in SQL, and the explicit rejection of summing in Node. Those are *properties*, and properties belong in a requirement. The exact column list and index shape are a **measured** decision — AC-B16 already demands a before/after measurement of rows scanned, bytes and latency — and pinning them here would freeze the answer that the measurement exists to produce. A requirement that dictates an index definition also quietly moves ownership of the query plan from Dev to BA, which is not where it belongs.

**One addition to FR-B11 instead**, because it is a property and not an implementation detail: **the 100-row cap is enforced inside the function**, not only by the route's Zod schema, so a caller reaching the RPC directly cannot widen it. AC-B11 currently says "rejected or clamped server-side" — make it say *where*. The mechanism stays Dev's choice.

**Q4 — Is the trailing exclusion window correctly left to Dev/SA? → Yes, correctly left. With two conditions, and one warning.**

Correct to leave it: it is a property of the audit write path, not a business preference.

- **Condition (a) — it must not be a magic number.** It derives from `AuditTrailService`'s batching: `batchSize: 100` and `batchIntervalMs: 5000` (`lib/services/AuditTrailService.ts:43-44`), flushed by a lazily-started, `unref`'d interval (`:260-265`).
- **Condition (b) — the boundary must be on screen.** "Actions in the last N minutes are not yet counted." A cut-off an operator cannot see is a cut-off they will misread. NFR-7 applies.
- ⚠️ **The warning, and it is the important half: do not size this window from `batchIntervalMs`.** Five seconds is an in-process timer. This runs on Vercel, where the function instance can be frozen or torn down before the timer fires and the queued entries are simply gone — **that is KI-B**, which is why Layer 3 recorded it as a known issue rather than a latency. A window derived from 5 s would be a rigorous-looking number that is wrong by orders of magnitude. Size it **conservatively, in minutes**, document it as a deliberately generous floor rather than a derivation, and put the reasoning in the code comment.
