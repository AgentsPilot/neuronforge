# Requirement: Test Account Cleanup — Inbound FK Drift Guard (Jest)

> **Last Updated**: 2026-10-30

**Created by:** BA
**Date:** 2026-10-30
**Status:** SA approved with conditions (2026-10-30). See § SA Review

## Overview

`public.operator_test_account_cleanup` is generated by `scripts/generate-test-account-cleanup-sql.ts`. Its runtime guard G-18 refuses every foreign key *into* a table the cleanup empties unless the generator lists it in `INBOUND_FOREIGN_KEYS`. When another stream's migration adds such an FK without touching the generator, G-18 blocks every check, hard delete and anonymise on prod (admin Danger Zone and owner self-delete). This requirement adds a static Jest guard in the existing PR gate that catches the drift at PR time, before the migration reaches prod.

---

## Problem

The same outage has happened twice:

| # | Cause | Fix |
|---|---|---|
| 1 | Commit `c21a4b0f` added `abandoned_bookings` / `scheduling_meetings` to the plan without their inbound links | Migration 20261092 ([workplan](/docs/workplans/TEST_ACCOUNT_CLEANUP_MEETINGS_FK_FIX_WORKPLAN.md)) |
| 2 | Migration 20261097 added `scheduling_meetings.replaces_meeting_id REFERENCES scheduling_meetings(id)` | Migration 20261101, PR #580 (`fix/cleanup-g18-meeting-replaces`), **not yet merged** |

G-18 is correct to fail closed — the defect is that nobody learns about it until a live check runs. Nothing in CI connects "a migration added an FK" to "the cleanup generator must review it".

## Goal

A PR that adds an FK into a cleanup-plan table, without the matching generator review, turns the existing Jest gate red with a message that says exactly which FK to review and how.

---

## User Stories

- As a developer on any stream, I want my PR to fail when my migration adds an FK the account cleanup has not reviewed, so that I fix it in the same PR instead of breaking account deletion on prod.
- As the operator / account owner, I want delete and anonymise to keep working after unrelated releases.
- As a reviewer, I want the failure to name the migration, the FK and the procedure, so the fix takes minutes.

## Scope

**In scope**
- A Jest test under `scripts/__tests__/` (collected today by `npm run test:gate`, `.github/workflows/tests.yml`).
- Static parsing of `supabase/migrations/*.sql` for FK constraints whose parent is a table in `buildCleanupPlan('hard')` (superset; anonymise = hard minus `KEEP_SET`, so it covers both modes).
- Cross-check against `INBOUND_FOREIGN_KEYS` and `PARENT_OWNED_REASONS` in the generator.
- A negative control proving the guard can fail.

**Out of scope**
- Any change to the runtime guards G-18 / G-10 or to the generated function.
- Any live DB query, Supabase MCP call, or new CI workflow / job.
- Auto-fixing the generator or auto-generating `INBOUND_FOREIGN_KEYS`.
- FKs whose child is in the plan but whose parent is neither a plan table nor `auth.users` (neither runtime guard trips on them).
- auth.users (G-10 class) links — **pending OQ-1**.

## Functional Requirements

**FR-1 — Collect FKs from migrations.** The guard reads every `supabase/migrations/*.sql` (CRLF-normalised, same as `readSql` in `testAccountCleanupSql.test.ts`) and extracts each FK it declares: inline `col type REFERENCES t(c)` in `CREATE TABLE`, `ALTER TABLE ... ADD COLUMN ... REFERENCES`, table-level `FOREIGN KEY (...) REFERENCES`, and `ADD CONSTRAINT name FOREIGN KEY`. Comments and string literals must not produce matches.
- AC-1: Each extracted FK records migration file, child schema.table, child column(s), parent schema.table, and constraint name.
- AC-2: An FK in a `--` or `/* */` comment, or inside a quoted string outside dynamic-SQL handling (FR-5), is not reported.

**FR-2 — Resolve the constraint name.** When no name is given, apply the Postgres default `<table>_<column>_fkey` (including Postgres's 63-byte truncation rule). Explicit names are taken as written.
- AC-3: `ALTER TABLE scheduling_meetings ADD COLUMN replaces_meeting_id uuid REFERENCES scheduling_meetings(id)` resolves to `scheduling_meetings_replaces_meeting_id_fkey`.

**FR-3 — Follow later changes.** Apply, in filename order, `DROP CONSTRAINT [IF EXISTS]`, `RENAME CONSTRAINT`, `DROP TABLE`, `DROP COLUMN` and table renames, so the guard judges the constraint as it stands after the last migration, not as first written.
- AC-4: A constraint added in one migration and dropped in a later one is not reported.
- AC-5: A renamed constraint is checked under its final name.

**FR-4 — Filter to the cleanup plan.** Keep only FKs whose parent is a `public` table in `buildCleanupPlan('hard')`. Self-references (child = parent) are included.
- AC-6: `scheduling_meetings → scheduling_meetings` is in scope.

**FR-5 — Dynamic SQL.** FKs built inside `DO` blocks / `EXECUTE format(...)` (e.g. `20260916_business_data_ownership.sql`, `<table>_business_fk` in a loop) cannot be parsed reliably. Handling is **pending OQ-4**; whatever is chosen, an unparsed dynamic FK must never pass silently.
- AC-7: A migration containing `EXECUTE` with `REFERENCES` / `FOREIGN KEY` text that the guard does not handle fails the guard unless it is on the reviewed list chosen in OQ-4.

**FR-6 — Cross-check against the generator.** Each in-scope FK passes only if `(child_table, constraint_name)` is in `INBOUND_FOREIGN_KEYS`; if that entry's owner column is `null`, the parent must also have a `PARENT_OWNED_REASONS` entry (mirrors G-18). Historical FKs are handled per OQ-2.
- AC-8: On a tree with PR #580 merged, the guard passes.
- AC-9: On `main` today (before #580), the guard fails on `scheduling_meetings_replaces_meeting_id_fkey` from 20261097. This is the guard working.

**FR-7 — Failure message.** One line per unreviewed FK, then the procedure once:
```text
Unreviewed foreign key into a cleanup-plan table — G-18 will block every
check, delete and anonymise on prod once this migration is applied.

  20261097_<name>.sql: public.scheduling_meetings.replaces_meeting_id
    -> public.scheduling_meetings  (constraint scheduling_meetings_replaces_meeting_id_fkey)

Fix in scripts/generate-test-account-cleanup-sql.ts:
  1. Add [child_table, constraint_name, owner_column | null] to INBOUND_FOREIGN_KEYS
     (null owner -> add a PARENT_OWNED_REASONS entry with the reason).
  2. Bump FUNCTION_MIGRATION as the comment block above it describes.
  3. Run: npx tsx scripts/generate-test-account-cleanup-sql.ts and commit the output.
```
- AC-10: The message names file, child table.column, parent, and constraint name for every offender, not just the first.
- AC-11: It names the generator path, both arrays, `FUNCTION_MIGRATION`, and the regenerate command.

**FR-8 — Negative controls.** The test suite runs the same checker on synthetic input.
- AC-12: A synthetic migration adding `ALTER TABLE public.<plan table> ADD COLUMN x uuid REFERENCES public.<plan table>(id)` with no generator entry makes the checker report exactly that FK.
- AC-13: The same synthetic FK followed by a synthetic `DROP CONSTRAINT` is not reported (proves FR-3).
- AC-14: A synthetic `EXECUTE format('... REFERENCES ...')` block not on the reviewed list is reported (proves FR-5 fails closed).
- AC-15: The checker reports zero FKs from a commented-out `REFERENCES` line (proves AC-2).

## Non-Functional Requirements

- **Performance / CI time:** runs inside the existing `test:gate` Jest job; no new workflow, job or step. Target well under 2 s for ~300 migration files (file reads + one tokenizer pass). Must not extend the CI critical path (`next build`).
- **No live DB:** purely static; no Supabase credentials, no network.
- **Determinism:** same input, same output; Windows CRLF must not change results (see Jest local-vs-CI flake patterns).
- **Security:** read-only over repo files; no change to the secret-gated function.
- **Maintainability:** the reviewed lists live next to the existing reviewed data in the generator (or wherever OQ-3 decides), each entry with a reason, matching the generator's "each entry carries its reason" convention.

That directory holds 295 entries, about 69.9k lines of `.sql`, and four `2026-08-14_*` files whose names are hyphenated. Probes run:
- `fk_payment_invoices_service` (20260809214450) is never dropped or renamed anywhere in the repo, yet the generator reviews the live name `payment_invoices_service_id_fkey`. This is drift between repo and prod, not a superseded name.

### Rulings

**SA-1 — OQ-1 (G-10 class): (b) in principle, with a measured exception.** Slice 1 covers G-18 only. G-10 is keyed on `(schema, table, column)`, so constraint names and the name-drift noise do not apply to it, and it reuses the same replay. The Dev's workplan must include a measurement step: run the replay once for FKs into `auth.users` and check each against `tenancyForeignKeys() ∪ ACTOR_FOREIGN_KEYS`. Record the count in the workplan.
- G-10 may join slice 1 only if both hold:
  - (i) it needs **≤ 5** reviewed-exception entries (SA-4 kinds), and
  - (ii) it finds **no** real unreviewed live FK.
- Otherwise G-10 becomes slice 2, recorded in this requirement with the measured count.
- If the measurement finds a real gap (an FK that G-10 would block on prod today), that is a production bug. It gets its own fix PR first, the way #580 did, and it is never allow-listed.
- **Outcome (2026-10-30):** measured 89 FKs into `auth.users` from outside the `auth` schema, 89 reviewed. That is 0 exceptions and 0 real gaps, so both thresholds are met. SA code review comment 3 ruled **include in slice 1**. The guard's second pass is keyed `(childSchema, childTable, childColumns[0])` against `tenancyForeignKeys() ∪ ACTOR_FOREIGN_KEYS` and reports width ≠ 1. On re-measure after the change it is still 89/89. See the [workplan](/docs/workplans/TEST_ACCOUNT_CLEANUP_INBOUND_FK_GUARD_WORKPLAN.md).

**SA-2 — OQ-2 (historical noise): (c), full-history replay. The cutoff (b) is rejected.** TL's reasoning stands. A cutoff trusts that every pre-baseline FK is still correct, and it misses a new migration that re-adds an old-pattern FK or renames a reviewed constraint. The replay costs under a second. SA's probe changes one detail of TL's framing: `fk_payment_invoices_service` was not dropped by a later migration. Prod carries a different name for the same link. The exception list therefore needs a **live-name alias** kind (SA-4b), not a "dropped by" kind.

**SA-3 — OQ-3 (where the parser lives): (b), approved as a new pure module.**
- Put it at `scripts/lib/migrationForeignKeys.ts`, next to `scripts/lib/pgSchema.ts`.
  - No I/O in the parse and replay functions: they take `{ file, sql }[]` and return the replayed FK set plus a list of problems.
  - The test does the `readdirSync` and the CRLF normalisation.
- Unit tests go in `scripts/__tests__/migrationForeignKeys.test.ts`. The guard goes in `scripts/__tests__/testAccountCleanupInboundFk.guard.test.ts`. Both names fit the existing `*.guard.test.ts` / `*.test.ts` collection, so neither needs a new CI job or step.
- **Do not reuse or move the existing `scan`.** It is tuned to generated output. It has no code tokens, no double-quoted identifiers, no nested `/* */`, no `E'…'` backslash escapes, and its dollar tags cannot contain digits. Migrations need all of these: 10+ files use `E'`.
- The new module carries its own tokenizer, which emits code, comment, string and dollar-body tokens. The small duplication is justified, and `testAccountCleanupSql.test.ts` stays untouched.
- An unterminated comment, string or dollar body fails the guard and names the file (fail closed).

**SA-4 — OQ-4 (dynamic SQL): (a), an explicit reviewed list, which lives in the guard test file and not in the generator.** The generator stays read-only, so this slice needs no `FUNCTION_MIGRATION` bump. There are three exception kinds. Every entry carries a `reason`, and **every entry must match something in the replay, or the guard fails as a stale entry.** No entry is a blanket pass: each one feeds the normal check.
- **(a) `DYNAMIC_FK_MIGRATIONS`:** `{ file, sha256, expands: [{ child, columns, parent, constraint }], reason }`.
  - The sha256 is taken over the CRLF-normalised text, as `testAccountCleanupSql.test.ts:805` does.
  - The expansion is **injected into the replay at that file's position**. Later DROP/RENAME statements still apply to it, and the result is checked against `INBOUND_FOREIGN_KEYS` like any static FK.
  - Hand-expand `20260916_business_data_ownership.sql` from its `business_owned` array. Do not evaluate `format()` (that was option (c), which is rejected).
- **(b) `LIVE_NAME_ALIASES`:** `{ file, child, repoName, liveName, reason }`. The replay renames `repoName` to `liveName`, and the normal check then applies to `liveName`. `fk_payment_invoices_service` → `payment_invoices_service_id_fkey` is the known case.
- **(c) `NOT_ON_PROD`:** `{ file, child, constraint, reason }`. This is for an FK the repo declares that does not exist on prod, for example from a duplicate `create_*_tables` file that never ran or a table dropped out of band.
- For (b) and (c), the reason must cite the read-only live check made when the entry was written, using the `business-os-schema-check` skill. CI never queries the database.
- **Dynamic detection is token-based, not file-based.** FK syntax counts as dynamic when it appears inside a string-literal token at any depth, or inside a non-`DO` dollar body such as a `CREATE FUNCTION` body. FK syntax means `REFERENCES <ident>[ (` or `FOREIGN KEY (`/`%`. Each such case fails the guard unless its file is in (a) with a matching sha256.
  - `EXECUTE FUNCTION` and prose such as `COMMENT ON … IS '… references …'` must not trip it.
  - This replaces the wording of AC-7.

**SA-5 — Replay semantics (refines FR-2 / FR-3).** These rules let the Dev build the replay without guessing:
1. **File order.** Read only `supabase/migrations/*.sql` (not sub-directories, `.md` files or `__tests__`). Sort by plain code-unit comparison, not `localeCompare`. The four hyphenated `2026-08-14_*` files then sort first. That is acceptable: if their real order matters for any FK, handle it with an SA-4 entry.
2. **Identifiers.** Unquoted names fold to lower case. Quoted names are taken as written. An unqualified table means `public`. `REFERENCES t` with no column list targets the primary key, recorded as an unknown column, which is fine because G-18 keys on the constraint name.
3. **Statements inside `DO $$ … $$` bodies** are parsed as static DDL and treated as executed. This covers the common `IF NOT EXISTS … THEN ALTER TABLE … ADD CONSTRAINT` idiom.
4. **`IF NOT EXISTS` behaves as Postgres does.** `CREATE TABLE IF NOT EXISTS` on a table the replay already holds adds nothing. `ADD COLUMN IF NOT EXISTS` on an existing column adds no FK.
5. **Default names.** Use `<table>_<col1>[_<col2>…]_fkey`, truncated per Postgres `makeObjectName`: shorten the longer of the table part and the column part until the name fits in 63 bytes. Add a unit test for a name over 63 bytes. Postgres's numeric suffix on collision (`_fkey1`) is modelled from the replayed table's existing names.
6. **Changes the replay must follow.**
   - Apply `DROP CONSTRAINT [IF EXISTS]`, `RENAME CONSTRAINT`, `DROP COLUMN` (drops the FKs on that column) and `ALTER TABLE … RENAME TO` (the child table key changes; constraint names do not).
   - `DROP TABLE` removes the table's own FKs **and** every FK pointing at it, because Postgres needs CASCADE for the drop to succeed.
   - `ALTER TABLE … RENAME COLUMN` changes the recorded column only.
7. **Unknown statements are ignored.** The parser only has to recognise the statement shapes above. Anything else can carry no FK unless it contains FK syntax. FK syntax that the parser cannot attribute to a recognised statement fails closed, naming the file and line.

**SA-6 — What the check must also catch (adds to FR-6).** G-18 blocks **every** FK into a plan table whose `key_width <> 1`, even a reviewed one: the `inbound_rows.key_width <> 1` blocking condition. So a multi-column FK into a plan table is reported with its own message saying G-18 cannot accept it.
- The `PARENT_OWNED_REASONS` clause in FR-6 is mis-keyed. The map is keyed by the **child** table, and `testAccountCleanupSql.test.ts` (~396–398) already enforces "null owner ⇒ reason". The guard must not repeat that check. It checks only `(child_table, constraint)` ∈ `INBOUND_FOREIGN_KEYS`, plus `child_schema = 'public'`, mirroring `inbound_joined.reviewed`.
- The plan scope is `buildCleanupPlan('hard')`, as written.
- The guard checks in one direction only. Extra `INBOUND_FOREIGN_KEYS` entries for tables that exist only on prod are not errors. FKs that exist only on prod stay G-18's runtime job, and that limit is stated in the guard's header comment.

**SA-7 — CI time.** The guard runs inside `npm run test:gate` with no new workflow, job, step or config change. `jest.gate.config.js` already collects both test files. The workplan records the measured local time of the guard file. The budget is under 2 s, and above that SA must rule before merge. The guard must not read files outside `supabase/migrations/` and the generator import.

**SA-8 — Landing order: confirmed.**
- PR #580 (`origin/fix/cleanup-g18-meeting-replaces`) merges to `main` first.
- The guard branch is cut from `main` **after** that merge. It is not stacked on #580.
- `scheduling_meetings_replaces_meeting_id_fkey` must never appear on any exception list.
- Before #580 merges, the Dev proves AC-9 by running the guard against a pre-#580 tree, or against the current tree with the #580 entry removed locally. Paste the red output into the workplan and into the PR description. That output must match FR-7.
