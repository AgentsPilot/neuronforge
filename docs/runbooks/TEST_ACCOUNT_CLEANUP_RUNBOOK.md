# Test Account Cleanup Runbook

> **Last Updated**: 2026-10-08

## Overview

This runbook covers removing ONE test account completely, login included, so the same email can be invited and sign up again. It is done with two SQL files pasted into the Supabase SQL editor:

| File | What it does |
|---|---|
| `scripts/test-account-cleanup-check.sql` | Read-only. Lists what would be removed and everything that blocks it. Ends with **OK** or **BLOCKED** |
| `scripts/test-account-cleanup-delete.sql` | Removes everything in one block: either all of it or nothing. Ends with **CLEAN** |

This is operator exception **OX-1r** (it revises OX-1): the same generated logic also runs from the admin-only `/api/admin/test-account-cleanup/*` routes, through the single secret-gated database function `public.operator_test_account_cleanup` (setup and rollback: section 6). The Danger Zone section of `/test-business-os` will call those routes (slice 2). They delete the storage files the check lists before the delete, and record the admin as the actor. This pasted form stays as the fallback (BQ-6). It is not a product feature, and it is not the admin delete (that one keeps the login and never frees the email, UD-1). It runs as the database owner, so row security protects nothing: the checks in the files are the only safety. Never edit the SQL by hand. It is generated by `scripts/generate-test-account-cleanup-sql.ts`, and a test fails if the two drift apart.

---

## 1. Edit the lines at the top

Each file starts with lines you edit. Change only the text inside the quotes.

| Line | Check file | Delete file | What to type |
|---|---|---|---|
| `cleanup.target_email` | yes | yes | The email of the test account |
| `cleanup.test_tag` | yes | yes | The test tag. Default `+test` |
| `cleanup.confirm_email` | no | yes | The same email again |

**The test tag.** An account can be removed only when its email **contains** the tag. Case does not matter, and `%` or `_` are read as plain characters. The tag is free text: `+test` matches `name+test1@gmail.com`. You can also put a full address (`someone@walla.co.il`) or any fragment of one. An empty tag, or one that is only spaces, stops both files, because it would match every account.

## 2. Run the check

1. Open a **new** query tab in the Supabase SQL editor.
2. Paste the whole check file, edit the lines, and run it all at once.
3. Read the first row:

| Verdict | Meaning |
|---|---|
| **OK** | Nothing blocks. The row also shows how many rows will be removed |
| **BLOCKED** | Do not run the delete. Each `guard` row marked BLOCKED says what is wrong and how to clear it |

The other sections:

- `remove`: the rows per table that will go.
- `storage`: files you must delete first.
- `trigger`: the triggers on the login, each with the events it fires on. Only those marked "Fires when the login is deleted" run during the delete.
- `kept`: what stays.

## 3. Empty the storage folders, if any are listed

The SQL never deletes stored files (SA ruling C-4).

1. If the check lists `storage` rows, open **Storage** in the Supabase dashboard.
2. In each bucket shown, delete the folder named after the login id.
3. Run the check again until it shows OK.

## 4. Run the delete

1. Open a new tab and paste the whole delete file.
2. Edit the three lines (the email, the tag, and the email again) and run it all at once.

**Reading the result.** The last result is a report:

- One row per table, in table-name order. The `line` column is the table and `rows_removed` is how many of its rows were removed.
- A final **TOTAL** row. `rows_removed` there is the sum of the rows above, and `tables_removed` is how many tables they came from. It also shows the `result` (below), the `removed_login` id, `removed_at`, and `same_run`.
- Rows removed automatically by a cascade from a deleted parent (for example `crm_activities` with `crm_contacts`) are gone but not listed in the report, so the TOTAL can be lower than the check's "Rows to remove".

The report is read back from the audit row of the most recent removal in the last 15 minutes. With no such removal, the report is only the TOTAL row, showing NO RECENT REMOVAL. The login itself is not one of the table rows: CLEAN means it is gone too.

| Result (TOTAL row) | Meaning |
|---|---|
| **CLEAN** | Done, and proven before it was saved: the block checks that nothing still names the login and rolls everything back if anything does. One audit row, `BUSINESS_TEST_ACCOUNT_REMOVED`, records it, with counts and no email. `same_run` is true |
| An error starting `BLOCKED, nothing was removed` | Something changed since the check. Run the check again |
| Any other error | The whole block was rolled back and nothing was removed. Send the message to engineering |
| **REMOVED EARLIER** | A removal was saved in the last 15 minutes, but not by this run (`same_run` is false). Run the check file to see where things stand |
| **NO RECENT REMOVAL** | No removal was saved in the last 15 minutes. If no error was shown either, do not assume anything: run the check file. If it says G-1 "exactly one login has this email" is BLOCKED, the account is gone. If it says OK, the account is still there |

Running the delete again after CLEAN stops at G-1, because no login has that email any more.

## 5. Invite the email again

1. Send a new invitation to the same email from the same place you used before: the admin invite, or the friend invite of the same inviter.
2. Sign up.

What is kept: the invitation that first brought the account in, as the record of what the inviter did. What is removed: invitations the test account sent itself, and its own place in the invitation circle. The activity history recorded against the account goes too, including admin actions recorded on it.

⚠️ For a friend invite, check that the inviter can still invite this address. The kept, used invitation may still count against the inviter's friend allowance (SA, T9). If it does, use an admin invite, and tell engineering.

## 6. The Danger Zone path: one-time setup, checks and rollback

The admin routes call one database function, `public.operator_test_account_cleanup`, created by `supabase/migrations/20261041_operator_test_account_cleanup.sql` and replaced by each newer version (6.1.1). It runs the same guards as the files above. It refuses (error 42501) unless the server sends a second secret, `TEST_CLEANUP_SECRET`. The database keeps only the secret's sha256, never the secret itself. Until all the steps below are done, the routes answer 503 "not configured", and nothing can be removed.

### 6.1 Apply the migration

Paste `supabase/migrations/20261041_operator_test_account_cleanup.sql` into the Supabase SQL editor and run it once. It ends with `NOTIFY pgrst, 'reload schema'`. It fails loudly if the schema `operator_private` already exists: stop and ask engineering. Then apply every newer function version in date order (6.1.1).

The schema, the secret table and the stored hash stay, so 6.2 to 6.4 are not repeated. If two branches both change the cleanup plan, whichever lands second rebases onto the first one's generator, takes the next free number, sets `PREVIOUS_FUNCTION_MIGRATION` to the first one's file, adds the first one's sha256 to the `APPLIED` pins in `scripts/__tests__/testAccountCleanupSql.test.ts` once it is applied, and regenerates.

**Timing with the deploy.** The app pins the stamp the function returns (`lib/business-os/test-account-cleanup/cleanupFunctionVersion.generated.ts`). While the database function and the deployed build disagree, the Danger Zone check and delete refuse (they fail closed, nothing is removed). So apply the new version right before the build that pins it goes to Production (for 20261042: after 20261027, before the P-3b.1 deploy). The pasted check and delete files of that build also need the new tables, so do not paste them before 20261027 either.

To see which version the database holds, run this read-only query and compare `applied_version` with `CLEANUP_FUNCTION_VERSION` in the file above:

```sql
SELECT
  pg_catalog.split_part(pg_catalog.split_part(proc.prosrc, 'jsonb_build_object(''version'', ''', 2), '''', 1) AS applied_version,
  pg_catalog.strpos(proc.prosrc, 'business_os_billing_events') > 0 AS knows_billing_events
FROM pg_catalog.pg_proc AS proc
WHERE proc.oid = 'public.operator_test_account_cleanup(text, text, text, text, uuid, text)'::regprocedure;
```

After 20261042 the expected answer is the 20261042 stamp and `true`. Then rerun the lock check (6.5): it must still answer `false, false, true, false`.


### 6.2 Make the secret and its hash, on your own computer

Run this in **PowerShell**. It prints the secret and its sha256. Nothing leaves your computer.

```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
$secret = -join ($bytes | ForEach-Object { $_.ToString('x2') })
$hash = -join ([System.Security.Cryptography.SHA256]::Create().ComputeHash([System.Text.Encoding]::UTF8.GetBytes($secret)) | ForEach-Object { $_.ToString('x2') })
"secret: $secret"
"sha256: $hash"
```

The secret is 64 hex characters, and the hash is 64 more. In Git Bash the same is `S=$(openssl rand -hex 32); echo "$S"; printf %s "$S" | sha256sum`.

### 6.3 Store only the hash in the database

In the SQL editor, run this once with the **hash** (never the secret):

```sql
INSERT INTO operator_private.secrets (name, secret_sha256) VALUES ('test_account_cleanup', decode('<the 64-hex sha256>', 'hex'));
```

To rotate later, run `UPDATE operator_private.secrets SET secret_sha256 = decode('<new hash>', 'hex') WHERE name = 'test_account_cleanup';` and change the Vercel value. To disarm at once on the database side, run `DELETE FROM operator_private.secrets WHERE name = 'test_account_cleanup';`.

### 6.4 Set the secret in Vercel, Production only

Vercel, then Project, Settings, Environment Variables. Add `TEST_CLEANUP_SECRET` with the **secret** (not the hash), and tick **Production only**. Untick Preview and Development: preview builds run branch code from this public repository against the same database. Then redeploy Production. Close the PowerShell window afterwards so the secret is not left on screen.

### 6.5 Check the locks

Run in the SQL editor. The expected answer is `false, false, true, false`.

```sql
SELECT
  has_function_privilege('anon', 'public.operator_test_account_cleanup(text, text, text, text, uuid, text)', 'EXECUTE') AS anon_can_run,
  has_function_privilege('authenticated', 'public.operator_test_account_cleanup(text, text, text, text, uuid, text)', 'EXECUTE') AS signed_in_can_run,
  has_function_privilege('service_role', 'public.operator_test_account_cleanup(text, text, text, text, uuid, text)', 'EXECUTE') AS server_can_run,
  has_table_privilege('service_role', 'operator_private.secrets', 'SELECT') AS server_can_read_hash;
```

In the dashboard, open Settings, then API, then Exposed schemas. `operator_private` must **not** be listed.

Check the timeouts the server's requests run under:

```sql
SELECT rolname, rolconfig FROM pg_catalog.pg_roles WHERE rolname IN ('authenticator', 'service_role');
```

Any `statement_timeout` there must be longer than one check takes. Time the first check (6.6). If it is close to the limit, or the check fails with a timeout, stop and ask SA. Do not change the role setting yourself.

### 6.6 One live run

Before the **first** live delete, run this read-only step once and paste the result in the workplan:

```sql
SELECT trg.tgname, trg.tgtype, trg.tgfoid::regproc AS function_name
FROM pg_catalog.pg_trigger AS trg
WHERE trg.tgrelid = 'auth.users'::regclass AND NOT trg.tgisinternal;

SELECT trg.tgname, proc.proname, proc.proconfig, proc.prosrc
FROM pg_catalog.pg_trigger AS trg
JOIN pg_catalog.pg_proc AS proc ON proc.oid = trg.tgfoid
WHERE trg.tgname = 'trigger_update_storage_on_delete';
```

The first lists the triggers that fire when a login is deleted. The second prints the source and settings of the function behind the storage-quota delete trigger, which is not in the repository.

For the first live delete, pick a `+test` account that has at least one `payment_refunds` row and one `storage_usage` row, so the refund and storage-quota triggers run on purpose, not by accident.

On a `+test` account only: run one check, then one delete, from the Danger Zone (or, until that section ships, from the browser console while signed in as an admin, with `fetch('/api/admin/test-account-cleanup/check', ...)`, then `.../delete`). The check must say OK, or BLOCKED with only G-12. The delete must end with TOTAL = CLEAN. Then invite the email again (section 5).

**The 8-second limit (SA C-3).** The server's requests stop after 8 seconds, and a delete does more work than a check. Each answer carries `serverMs`, the time the database spent (the check route returns a number; the delete returns `{ check, delete }`), and the server log records it next to `elapsedMs`. If the check's `serverMs` is above 3000, or any delete times out, do not retry from the Danger Zone: clean that account with the pasted files (sections 1 to 5), which run the same guards in the SQL editor without the 8-second limit, and bring the numbers to SA. A timeout removes nothing. Never change a role's timeout.

### 6.7 Roll back

**One version back.** Run the newest version's rollback, for example `supabase/SQL Scripts/20261043_operator_test_account_cleanup_insight_links_rollback.sql` (it restores the 20261042 function). It restores the previous function byte for byte and keeps the schema, the secret table and the hash. Redeploy a build that pins the previous stamp, or the Danger Zone refuses.

**The whole feature.** Roll back each newer version first (newest first), then run `supabase/SQL Scripts/20261041_operator_test_account_cleanup_rollback.sql` in the SQL editor. It drops the function, the secret table and the schema. Then remove `TEST_CLEANUP_SECRET` from Vercel and redeploy. The pasted files above keep working without either.

## What blocks, and why

| Guard | Blocks when |
|---|---|
| G-1 | No login, or more than one, has the email |
| G-2 | The email does not contain the test tag, or the tag is empty |
| G-3 | The confirmation line differs from the email (delete file only) |
| G-4 | The account is a platform admin |
| G-5 | Anything ever ran in Stripe **live** mode |
| G-6 | A plan subscription is still live, in test or live mode. Cancel it in Stripe first |
| G-7 | Legacy billing rows carry a Stripe id. They have no mode, so they are treated as real money |
| G-8 | A Stripe account is connected for client payments |
| G-9 | Money is in flight: running plans, pending payments or refunds, unpaid invoices |
| G-10 | A link to the login names another account or platform data, or nobody has reviewed the link yet |
| G-11 | A column the script relies on is missing. Regenerate the script |
| G-12 | Stored files remain under the account folder |
| G-13 | Another account sits inside an organisation this login owns |
| G-14 | The account has consent-ledger rows. That ledger is append-only, so this script cannot remove such an account |
| G-15 | The account invited someone whose account still exists |
| G-16 | Another account imported an agent this account shared |
| G-17 | A trigger nobody has reviewed sits on a table the script empties, or on a table the login delete reaches |
| G-18 | A row of another account points at something the script removes, so it would be deleted or emptied with it. Or such a link has not been reviewed yet |
| G-19 | Removing a row would empty a NOT NULL column of another table this script empties later (ON DELETE SET NULL or SET DEFAULT), which the database refuses with 23502. A plan defect, never an account one: engineering reorders the generator |
